# BI Copilot — governed self-serve analytics for SQL + business documents

Ask a business question in plain English. A LangGraph agent routes it to a
governed SQL warehouse, a cited document index, or both, then returns one
answer with sources, a chart, and an audit-log entry. Alongside the chat it
ships an executive KPI dashboard, a library of analyst SQL, automated data
quality checks, and an evaluation harness that gates CI.

## The problem

Stakeholders wait on analysts for routine numbers, and the answer is usually
split across a warehouse and a pile of policy or performance documents. Two
things go wrong: numbers arrive without context, and narrative claims arrive
without anyone checking them against the data.

## What this project does about it

| Capability | Where | Why it matters |
|---|---|---|
| **Natural-language Q&A** routed to SQL, documents, or both | `src/agent.py` | Self-serve answers with citations on every response |
| **Semantic metric layer**: one definition each for revenue, COGS, gross margin, AOV and more | `src/metrics.py` | "Revenue" means the same thing in chat, dashboard and SQL library; a test enforces it |
| **Analyst SQL library**: 8 queries covering CTEs, window functions, cohorts, RFM and Pareto | `sql/analysis/` | Answers to recurring business questions, all reviewable |
| **Executive dashboard**: QoQ KPI cards, trend, category margin, discount, RFM, cohorts | `app.py` | The weekly business-review view |
| **Insights report** built from the data, with no hand-typed numbers | `reports/insights.md` | Findings plus recommendations |
| **Data quality gate**: 9 checks covering duplicates, dates, negatives, casing and referential integrity | `src/load_data.py` | The pipeline fails before bad data reaches anyone |
| **Governed SQL**: one `SELECT`/CTE only, keyword blocking, read-only connection, row cap | `src/sql_guard.py` | The LLM proposes SQL; code decides what runs |
| **Hybrid RAG**: vector search plus keyword re-ranking, with filename citations | `src/agent.py` | Exact business terms are not lost to fuzzy embeddings |
| **Audit log**: question, route, exact SQL, sources, latency, error | `src/audit.py` | Lets you answer "why did the bot say that?" |
| **Evaluation harness**: golden questions scored on routing, answers and citations | `src/evaluate.py` | Regressions fail CI instead of reaching users |
| **CI + Docker** | `.github/workflows/ci.yml`, `Dockerfile` | Lint → build → test → eval gate on every push |

## Key findings (Q3 2026 vs Q2 2026)

Generated by `python -m src.analytics`. Full tables are in
[`reports/insights.md`](reports/insights.md).

1. **Growth is volume-led:** revenue rose **+20.1%** to $33.5K on **+32.1%** more orders, but **AOV fell 9.1%**.
2. **The "8% margin drop" in the Q3 summary is not supported by the warehouse.** Product gross margin *rose* from 55.3% to **56.5% (+1.2 pts)**. If margins fell, the cause is freight, and freight is not in the data. Recommendation: load carrier invoices before acting on the 8% figure.
3. **Footwear is the largest category (33% of revenue) and the least profitable per dollar (53.4% margin).** Footwear pricing and supplier cost are the biggest margin levers.
4. **Deep discounts give away margin without buying volume.** Orders discounted more than 15% earn 47.5% margin vs 58.8% at full price, and their basket is *smaller* (2.52 vs 2.74 units).
5. **41 high-value customers are "At Risk"** (RFM), holding 35.2% of lifetime revenue. They are the first win-back target.
6. The top 10% of customers drive 29.2% of revenue. 44.8% of a monthly cohort buys again within 3 months.

Finding 2 is the point of the project: the copilot doesn't repeat a document's
claim. It checks the claim against the data and says when the two disagree.

## Architecture

```text
 raw CSVs ──► load_data (clean + 9 DQ checks) ──► SQLite warehouse ◄── metrics.py (semantic layer)
                                                       ▲      ▲
 docs/*.txt ──► build_rag (chunk + embed) ──► ChromaDB │      │ sql/analysis/*.sql
                                                 ▲     │      │
                 ┌───────────────────────────────┼─────┼──────┼──────────────┐
                 │ Streamlit                     │     │      │              │
                 │  Chat ─► LangGraph supervisor ─► route: sql | docs | both │
                 │            ├─ sql specialist ── guard ── read-only SQL ───┘
                 │            ├─ doc specialist ── hybrid retrieval
                 │            └─ synthesize ── citations ── audit log
                 │  Dashboard · SQL Runner · Data Explorer · Data Quality · Audit Log
                 └────────────────────────────────────────────────────────────
```

The LLM never executes SQL. It proposes a query, the guard validates it, and a
connection opened with `mode=ro` plus `PRAGMA query_only` runs it. Wrapping the
query in an outer `LIMIT` enforces the row cap inside SQLite itself.

## Power BI report

[`powerbi/BI_Copilot.pbip`](powerbi/BI_Copilot.pbip) is a Power BI Project
(TMDL semantic model + PBIR report) over the same cleaned warehouse.

| Page | What it answers |
|---|---|
| Executive Overview | Q3 KPI cards with QoQ deltas, a dynamic margin-check narrative, revenue by category and region, category profitability |
| Trends | Monthly revenue with a 3-month rolling average, gross margin by month, MoM growth |
| Margin & Discounts | Q3 vs Q2 margin by region; margin, basket size and AOV by discount band |
| Customers | Top-10% revenue share, repeat rate, loyalty-tier revenue, customer ranking |

**Model:** star schema (`Orders` fact; `Products`, `Customers`, `Date` dimensions)
with 21 DAX measures in display folders (Core, Time comparison, Customers,
Narrative). Each measure mirrors a definition in `src/metrics.py`, and
time intelligence uses `DATEADD` / `DATESINPERIOD` on a marked date table.

**Open it:** run `python -m src.pipeline` (or `python -m src.export_powerbi`)
to write `powerbi/data/*.csv`, open `BI_Copilot.pbip` in Power BI Desktop, set
the `DataFolder` parameter (Transform data → Manage parameters) to your clone's
`powerbi/data/` folder, then Refresh.

**Verified against Python:** each DAX measure was run against the live model
and matches the SQL/Python results. Examples: Q3 revenue $33,522 (+20.1% QoQ),
181 orders, AOV $185.21 (−9.1%), gross margin 56.5% vs 55.3%, category and
discount-band margins, the 9-month rolling average, top-10% customer share
29.2%, and repeat rate 65.6%. Orders with no region (6.6% of Q3 revenue) are
excluded from regional visuals, as in the SQL library.

**Report as code:** pages and visuals are generated by
[`powerbi/tools/build_report.py`](powerbi/tools/build_report.py), so layout
changes are reviewable diffs.

## Evaluation

`python -m src.evaluate` runs [`evals/golden_questions.json`](evals/golden_questions.json):
10 questions covering SQL, documents, combined answers and small talk. It
checks the route, expected rows and columns, required phrases, and the
Sources section.

| Metric (offline mode) | Score |
|---|---|
| Routing accuracy | 100% |
| Answer checks | 100% |
| Citation coverage | 100% |
| p50 latency | ~5 ms |

CI fails if the pass rate drops below 90%. The harness surfaced two real bugs
during development: category questions were mis-routed to the product
ranking, and the offline embeddings missed the "discontinuations" passage.
Hybrid re-ranking fixed the second.

## Data and cleaning

`src/generate_data.py` writes three deliberately messy CSVs. `src/load_data.py`
cleans them, loads SQLite, and writes `data/quality_report.json`.

| Check | Issues found | Action |
|---|---:|---|
| Duplicate `order_id` | 10 | Keep latest record |
| Non-ISO `order_date` | 288 | Parse and normalize to `YYYY-MM-DD` |
| Null `unit_price` / `region` | 25 / 25 | Keep; excluded only from the metrics they affect |
| Negative `cost_price` | 1 | Replace with median valid cost |
| Untrimmed product names | 7 | Trim |
| Inconsistent `loyalty_tier` casing | 133 | Title-case |
| Orphan product / customer keys | 0 / 0 | Referential integrity gate |

Metric definitions live in [`src/metrics.py`](src/metrics.py). Revenue is
`quantity × unit_price × (1 − discount)`, booked revenue excludes `Cancelled`
and `Returned` orders, and gross margin uses product cost only (freight is not
stored).

## Quick start

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate    macOS/Linux: source .venv/bin/activate
pip install -r requirements-dev.txt
python -m src.pipeline          # data -> warehouse -> DQ checks -> index -> insights report
streamlit run app.py            # http://localhost:8501
```

The app also builds anything missing on first start, so a fresh clone or a
Streamlit Cloud deploy works without the setup step.

```bash
pytest -q                         # 23 tests: guard, agent, metric parity, DQ, evals
python -m src.evaluate --min 0.9  # scorecard -> reports/eval_results.md
ruff check .
docker build -t bi-copilot . && docker run -p 8501:8501 -e OPENAI_API_KEY=... bi-copilot
```

**Modes:** with `OPENAI_API_KEY` set, GPT-4o-mini handles routing, SQL
generation and synthesis, and OpenAI embeddings power retrieval (rebuild with
`python -m src.build_rag`). Without a key the project runs fully offline:
deterministic rules route questions, a template planner built on the metric
layer writes SQL, and local hashing embeddings drive retrieval.

## Limitations and next steps

- Sample data is synthetic and small (490 orders), chosen so every number can be checked by hand.
- Offline mode handles only the question shapes its templates cover. Open-ended SQL needs the LLM path, and the golden set should be re-scored in that mode.
- Not multi-tenant: no authentication or row-level security yet. Production would add SSO, a managed warehouse (Postgres, BigQuery or Snowflake), a hosted vector store, and secrets management.
- Next: load shipping cost so the margin question can be answered fully; add a dbt layer; extend evals with LLM-as-judge scoring for free-text answers.
